# ADR-015: Migration aracı, rol ayrımı ve dağıtım sırası

**Tarih / Durum:** 2026-10-05 · **kabul** (ADR-012 rev.: Supervisor kabul etti; security-reviewer turları @83b5bea → @251503f + son delta, BLOCKER 0 · MAJOR 0)

**Bağlam:**
- G-08: migration'lar genişlet–taşı–daralt; veri kaybettirmeyenlerde **down migration zorunlu**. `14 §CI`: migration ileri/geri CI'da. Birleşmiş migration korunan dosyadır (`MIGRATION_GLOBS` = `**/migrations/**`, `**/drizzle/**`).
- I-03: uygulama rolü (`wms_app`) tablo sahibi/süper kullanıcı/BYPASSRLS değildir; migration rolü ayrıdır. Yerel/CI'da `wms_migrator` (compose bootstrap kullanıcısı) + `wms_app` (`infra/postgres/init/01-roles.sh`). Neon karşılığı Q-06 / T-005d.
- Drizzle 0.45.3 kurulu; `drizzle-kit` kurulu değil. `drizzle-kit` yalnızca ileri (up) SQL üretir; down üretmez.

**Karar:** Seçenek A.
1. **Dosyalar:** `packages/db/migrations/NNNN_<snake_ad>.up.sql` + `.down.sql`, dört haneli artan numara. Her dosya tek transaction'da uygulanır (`CONCURRENTLY` gerektiren indeks ayrı, transaction dışı işaretli migration — ihtiyaç doğunca bu ADR'ye ek).
2. **Defter:** `wms_meta.schema_migrations(version, name, checksum_sha256, applied_at, applied_by)`; şema `wms_meta`'nın sahibi migration rolü; `wms_app`'in bu şemada **hiçbir yetkisi yok**. Özet `.up.sql` **ve** `.down.sql` içeriğini birlikte kapsar. Defter, koşu kilidi alındıktan **sonra** yeniden okunur (iki eşzamanlı koşturucu aynı migration'ı iki kez uygulayamaz). Uygulanmış bir migration'ın dosya özeti değişmişse koşturucu **durur** (`MIGRATION_CHECKSUM_MISMATCH`) — `check:protected`'a ek çalışma anı savunması.
3. **Koşturucu:** `packages/db/src/migrate.ts`; komutlar `pnpm db:migrate` (bekleyenleri uygula), `pnpm db:rollback -- --to <NNNN>` (yalnızca `WMS_ENV` ∈ `local|ci|staging`; prod'da gerçek veri kaybettiren down kullanıcı onayı ister — PROTOCOL §Onay kaynağı). Tek koşu kilidi: `pg_advisory_xact_lock` **doğrudan** bağlantıda (pooler'sız). Bağlantı **yalnızca** `DATABASE_URL_DIRECT` (migration rolü); `DATABASE_URL` (uygulama rolü) ile çalıştırılırsa ret.
4. **Roller migration'da yaratılmaz:** `wms_app`, `wms_auth` (ADR-014 §10) ve `wms_identity_probe` (`NOLOGIN NOSUPERUSER NOBYPASSRLS`, ADR-016 §9; migration rolünün bu role üyeliği ve probe rolünün şema yetkisi 3. tur eki m4'tedir — önceki "migration rolü `ADMIN`'idir" ifadesi PG16+ için yetersizdir) altyapı adımıdır (yerelde `01-roles.sh`, Neon'da T-105 hazırlık iş akışı). İlk migration (`0001_baseline`) `wms_app`'in varlığını ve `NOSUPERUSER NOBYPASSRLS NOCREATEROLE NOCREATEDB` olduğunu, `pg_auth_members`'ta hiçbir role üye olmadığını ve hiçbir nesnenin sahibi olmadığını **denetler**, değilse durur (`wms_auth` için aynı denetim `0002_identity`'de); `public` şemasında `CREATE`'i ve veritabanında `TEMP`'i `PUBLIC`'ten alır (`EXECUTE format('REVOKE TEMP ON DATABASE %I FROM PUBLIC', current_database())`); `wms_app`'e yalnızca `USAGE` verir. Her tablo yetkisi kendi migration'ında açıkça `GRANT` edilir (varsayılan yetki yok).
5. **RLS şablonu (her tenant tablosu):** `tenant_id uuid NOT NULL`, `(tenant_id, id)` benzersiz + bileşik FK, `ENABLE` + `FORCE ROW LEVEL SECURITY`, `USING` + `WITH CHECK` `tenant_id = NULLIF(current_setting('app.current_tenant_id', true), '')::uuid` (15 §DB sözleşmesi). Platform (global) tabloları RLS'siz olabilir ama yalnızca gereken `GRANT`'ları alır ve ADR-016'da listelenir.
6. **Drizzle şeması:** `packages/db/src/schema/*.ts` tip kaynağıdır; migration yerine geçmez. Sapma testi (`tests/integration/schema/drift.int.test.ts`): migration'lar uygulanmış veritabanında `information_schema` sütun adı/tipi/NULL'luğu Drizzle tablo tanımlarıyla birebir.
7. **Dağıtım sırası (staging/prod):** `deploy-staging.yml` → migration adımı (**uygulama dağıtımından önce**, doğrudan Neon bağlantısı, migration rolü) → Fly dağıtımı → smoke. Genişlet–taşı–daralt: yeni sürüm eski şemayla, eski sürüm yeni şemayla çalışabilmelidir; daraltma (sütun silme) ayrı ve sonraki dağıtımda.
8. **Test:** `pnpm test:int` her koşuda boş veritabanında tüm migration'ları uygular; ayrıca `migrations.int.test.ts` ileri → tümüyle geri → ileri döngüsünün hatasız olduğunu ve geri sonrası şemanın boş (yalnızca `wms_meta` defteri) kaldığını doğrular.
9. **Down kuralları (m6):** down migration up'ın açıkça verdiği şeyi geri alır, öncesinde var olan güvenlik ayarını gevşetmez (ör. `0001` down `PUBLIC`'e `CREATE`'i **geri vermez**). Veri kaybettiren down (tablo/sütun silme) hedef tabloda satır varsa `WMS_ENV` ∈ `local|ci` dışında `RAISE` ile durur (koşturucu `wms_meta.allow_destructive_down` oturum ayarını yalnızca bu ortamlarda açar).

**4. tur eki (security-reviewer delta @ c9195ef; MINOR-3, MINOR-4 ile bağlantılı):**
- **MINOR-3 — süper kullanıcı olmayan migration rolüyle probe sahipli işlevler.** `INHERIT FALSE` üyelikte migration rolü `wms_identity_probe`'un sahip olduğu işlevler üzerinde sahip yetkisi taşımaz; Neon'da (süper kullanıcı olmayan sahip rolü) `ALTER FUNCTION … OWNER`'dan sonra `DROP FUNCTION` / `CREATE OR REPLACE FUNCTION` başarısız olur. Yerelde migration rolü bootstrap süper kullanıcısı olduğundan fark yerel testte görünmez. Karar — **`SET ROLE` kalıbı** (`wms_identity_probe` sahipli her işlevin — yoklama işlevleri ve probe sahipli üyelik tetikleyici işlevi — DDL'i için zorunlu):
  1. Up: migration rolü (şema sahibi) `GRANT USAGE, CREATE ON SCHEMA wms_probe TO wms_identity_probe` → `SET ROLE wms_identity_probe` → işlevler `CREATE FUNCTION` ile **doğrudan probe sahipliğinde** oluşturulur (`ALTER … OWNER` gerekmez) → `RESET ROLE` → `REVOKE CREATE ON SCHEMA wms_probe FROM wms_identity_probe` (ADR-016 4. tur eki MINOR-4) → `EXECUTE` yetkileri (migration rolü işlevlerin sahibi olmadığından `GRANT/REVOKE EXECUTE` da `SET ROLE wms_identity_probe` bloğu içinde yapılır). Probe sahipli tetikleyici işlevinin `CREATE TRIGGER`'ı için migration rolüne `EXECUTE`: 5. tur eki MINOR-2.
  2. Değiştirme (sonraki migration'lar): aynı sıra; `CREATE` başta geçici verilir, sonda geri alınır.
  3. Down: `SET ROLE wms_identity_probe` → `DROP FUNCTION` (sahiplik yeterli, `CREATE` gerekmez) → `RESET ROLE` → `DROP SCHEMA wms_probe` (`RESTRICT`; şema sahibi migration rolü). Eşdeğer seçenek olarak şema sahibinin `DROP SCHEMA … CASCADE` ile içindeki başka sahipli nesneleri silebilmesi kurulu sürümde doğrulanırsa kullanılabilir; seçilen yol rapora (G-04).
  4. Her `SET ROLE` bloğu aynı migration dosyasında `RESET ROLE` ile kapanır ve migration'ın son ifadesi `current_user = session_user` denetleyen `DO` bloğudur (değilse `RAISE`); böylece defter yazımı probe rolüyle yapılamaz.
  5. Üyelik ön denetimi `pg_auth_members`'ta `roleid = wms_identity_probe AND member = current_user` olan **tüm satırlar** üzerinden yapılır (PG16+'da farklı yetki verenlerden birden çok satır olabilir): en az bir satır var, **hiçbir** satırda `inherit_option = true` yok, en az bir satırda `set_option = true`; değilse `RAISE`. (5. tur eki MINOR-6 ile genişletildi: `admin_option` şartı ve migration rolü dışındaki üyeler.)
  6. Test: `0003` ileri → geri → ileri döngüsü **süper kullanıcı olmayan** bir migrator rolüyle (Neon sahip rolü eşdeğeri: `NOSUPERUSER NOBYPASSRLS`, veritabanının sahibi, probe üyeliği `SET TRUE, INHERIT FALSE`) ayrı bir Testcontainers PostgreSQL örneğinde koşar (paylaşılan kümeye ek üye eklenmez; T-108'in "tek üye" denetimi bozulmaz). T-103.

**5. tur eki (security-reviewer delta @ 251503f; MINOR-2, MINOR-6 — MINOR-3 ADR-014'te, MINOR-4 ADR-014 ve ADR-016'da, MINOR-5 ADR-016'da; MINOR-1 kartlarda ve yukarıdaki üstü çizili satırlarda):**
- **MINOR-2 — `CREATE TRIGGER` ve tetikleyici işlevinde `EXECUTE`.** PostgreSQL'de `CREATE TRIGGER` çağıranın tabloda `TRIGGER` yetkisine **ve** tetikleyici işlevinde `EXECUTE` yetkisine sahip olmasını ister (süper kullanıcıda denetim atlanır; bu yüzden yalnızca süper kullanıcı olmayan migrator testinde görünür). Migration rolü tablonun sahibidir ama probe sahipli tetikleyici işlevinin sahibi değildir; "probe sahipli işlevlerde `PUBLIC` dahil `EXECUTE` yok" kuralı gereği örtük yetkisi de yoktur. Karar: `SET ROLE wms_identity_probe` bloğunda tetikleyici işlevi için `REVOKE EXECUTE … FROM PUBLIC` ve **migration rolüne açık `GRANT EXECUTE`** (rol adı `session_user`'dan, `format('%I')` ile); `CREATE TRIGGER` `RESET ROLE`'dan sonra migration rolüyle. Risk yok: `RETURNS trigger` işlevi doğrudan çağrılamaz (PostgreSQL yalnızca tetikleyici bağlamında çalıştırır) ve tetikleyici ateşlenirken `EXECUTE` denetlenmez; migration rolü zaten tablo sahibidir. Bu, §9'daki (ADR-016) "başka hiçbir rolde `EXECUTE` yok" kuralının yalnızca yoklama işlevleri için geçerli olduğunu, tetikleyici işlevinde tek istisnanın migration rolü olduğunu belirtir. Yetki adları/davranışı kurulu PostgreSQL 17'de uygulayıcı doğrular (G-04). Test: T-103 `migrations-nonsuper`, T-104 katalog taraması.
- **MINOR-6 — örtük `ADMIN OPTION` ve üyelik denetiminin yeniden yazımı.** PG16+'da `CREATEROLE` sahibi süper kullanıcı olmayan bir rol yeni rol oluşturduğunda oluşturucuya örtük olarak `ADMIN` seçenekli üyelik satırı eklenir; `createrole_self_grant` ayarı doluysa ek `SET`/`INHERIT` satırı da eklenir. Neon'da probe rolünü sahip/migration rolü oluşturursa migration rolünde `admin_option = true` satırı oluşur; bu, probe üyeliğini başka rollere dağıtma yetkisidir ve gerekmez (`SET ROLE` kalıbı yalnızca `SET` ister).
  1. **Denetim kuralı** (0003 ön denetimi, T-108, T-105 özeti; `roleid = wms_identity_probe` olan **tüm** `pg_auth_members` satırları): (a) `member = <migration rolü>` satırları: ≥1; hiçbirinde `inherit_option`; **hiçbirinde `admin_option`**; en az birinde `set_option`. (b) `member <> <migration rolü>` satırları: hiçbirinde `set_option` veya `inherit_option` yok (yalnızca `admin_option` olabilir — probe'u oluşturan altyapı rolünün örtük satırı); `member` `wms_app`/`wms_auth` değil. Bu biçim probe'u migration rolü dışında bir rol oluşturduğunda da doğru çalışır (önceki "her satırın `member`'ı migration rolü" denetimi o durumda haksız yere kırmızıydı). Migration'da `<migration rolü>` = `current_user`; T-108'de `DATABASE_URL_DIRECT` kullanıcısı.
  2. **Kaldırma yeri:** rol üyelikleri altyapı adımıdır (§4) — migration `REVOKE ADMIN OPTION` çalıştırmaz, yalnızca denetler (fail-closed). Yerel/CI: `01-roles.sh` bootstrap süper kullanıcısıyla probe'u oluşturur (süper kullanıcıya örtük satır eklenmez) ve üyeliği `WITH ADMIN FALSE, SET TRUE, INHERIT FALSE` verir (T-101b). Neon (T-105): probe'u oluşturan rol, oturumda `createrole_self_grant` boşken oluşturur; migration rolü oluşturucuysa önce `REVOKE ADMIN OPTION FOR wms_identity_probe FROM <migration rolü>` (gerekirse `GRANTED BY` ile örtük satırın yetki vereni) denenir. Kurulu Neon PostgreSQL'i bu geri almaya izin vermiyorsa (örtük satırın yetki vereni bootstrap süper kullanıcısı olduğundan) seçenek: probe'u migration rolü **dışındaki** bir altyapı rolü oluşturur ve migration rolüne yalnızca `SET TRUE, INHERIT FALSE, ADMIN FALSE` verir (oluşturucunun yalnızca-`ADMIN` satırı 1(b) gereği kabul edilir ve özete yazılır). İkisi de mümkün değilse T-105 BLOCKED ve bu ADR yeniden açılır. Davranış ve sözdizimi Neon'daki PostgreSQL sürümünde uygulayıcı doğrular (G-04, Q-05/T-005d).
  3. Test: T-103 `migrations-nonsuper` (`ADMIN TRUE` üyelik → `0003` `RAISE`); T-108 `roles.int.test.ts` kural 1; T-105 birim testi (sahte yanıtla `admin_option=true` → kırmızı).

**Sonuçlar ve riskler:**
- Elle senkron riski sapma testiyle kapatılır; test kırmızıysa paket birleşmez.
- Neon'da sahip rolünün (`neondb_owner` benzeri) migration rolü olarak kullanılabilirliği ve `wms_app`'in SQL ile oluşturulabilirliği T-005d sonucuna bağlıdır (Q-06). Olmazsa T-105 BLOCKED raporlar; bu ADR yeniden açılır.
- `pg-boss` kendi şemasını kurar: kurulum migration rolüyle (`pnpm db:migrate` sonunda), uygulama `migrate: false` ile bağlanır (T-115).

**Doğrulama:** `migrations.int.test.ts` (ileri/geri/ileri, özet uyuşmazlığında ret, `DATABASE_URL` ile çalıştırmada ret), `drift.int.test.ts`, staging dağıtım koşusunda migration adımının yeşil olması (T-106).
