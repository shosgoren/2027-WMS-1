# ADR-018: Stok komutu yürütme sözleşmesi — idempotency anahtarı, yeniden deneme, zaman aşımı, kilit sırası, eşik üstü işleme

**Tarih / Durum:** 2026-10-06 · **kabul** (Supervisor, ADR-012 rev.; security-reviewer @102140e 0·0·2, MINOR'lar işlendi — architect, T-201; 2. tur: security-reviewer @b70ce68 M-1, M-5, M-6, MINOR-2/3/7/12 işlendi; kabul PROTOCOL §Onay kaynağıyla)

**Bağlam:**
- `05 §İşlem sözleşmesi` 7 adımı ve `§Senkron işlem sınırları`nı tanımlar; idempotency anahtarını "tenant + işlem türü + istek özeti" olarak verir. I-06 ise "aynı anahtar + farklı içerik = ret; tekrar = önceki sonuç" der: anahtar içerikten türetilirse farklı içerik hiçbir zaman aynı anahtarı üretmez (Bulgu, T-201).
- AC-02/03 (tekrar, yanıt kaybı), AC-27 (deadlock sonrası yeniden deneme), AC-36 (eşik üstü belge worker'da, aynı anahtar). ADR-016 §6: worker kullanıcı adına yazarken güncel yetkiyle `withMembership`; yük `actorUserId` taşır.
- 1. tur incelemesi: reddedilen isteğin idempotency kaydı geri alınınca I-06'nın "farklı içerik" kolu işlemiyordu (M-1); worker yanlış aktör adına çalışıyordu (M-5); işleme sürerken belge iptal/yeniden işleme/rezervasyona açıktı (M-6); kalıcı hata "aynı transaction'da" kaydedilemezdi (MINOR-7).

**Seçenekler:**
| Seçenek | Artı | Eksi |
|---|---|---|
| **A. İstemci anahtarı + istek özeti + aktör; başarı aynı transaction'da, ret ayrı kısa transaction'da `REJECTED` olarak kalıcı** (seçilen) | I-06 tam: tekrar = önceki sonuç (başarı ya da ret), farklı içerik = `IDEMPOTENCY_MISMATCH`; yanıt kaybında da geçerli | Ret sonrası ikinci kısa transaction; aynı anahtarla "düzeltilmiş" yeniden deneme yapılamaz (yeni anahtar gerekir) |
| B. Ret sonrası anahtar serbest (kayıt geri alınır) | Tek transaction | I-06 "tekrar = önceki sonuç" ret için sağlanmaz; yanıtı kaybolmuş bir reddin tekrarı farklı sonuç verebilir |
| C. Anahtar = istek özeti (05 metni) | İstemci anahtarı gerekmez | Bilinçli iki aynı işlemden ikincisi sessizce yutulur |

**Karar:** Seçenek A.
1. **Anahtar:** `(tenant_id, command_type, client_key)`; `client_key` istemcinin ürettiği UUID (form açılışında üretilir; aynı formun yeniden gönderimi aynı anahtar). `request_hash` = komut girdisinin kanonik JSON'unun SHA-256'sı (anahtar sıralı; sunucu alanları — aktör, zaman — hariç). Kayıtta `actor_user_id` saklanır. Anahtar yoksa `VALIDATION_FAILED`/`IDEMPOTENCY_KEY_REQUIRED`.
2. **Başarı akışı (tek transaction, `05` adım 2–6):** `withMembership(permission)` → **hemen ardından** `set_config('lock_timeout'|'statement_timeout', …, true)` (A-75; benzersiz indeks beklemesi de sınırlı — MINOR-2) → `INSERT … ON CONFLICT DO NOTHING RETURNING` ile idempotency satırı (`IN_PROGRESS`); çakışmada satır `FOR UPDATE` okunur: `actor_user_id ≠ çağıran` → `IDEMPOTENCY_MISMATCH` (saklı sonuç başka kullanıcıya dönmez); `request_hash` farklı → `IDEMPOTENCY_MISMATCH`; `COMPLETED` → saklı sonuç; `REJECTED` → saklı hata kodu (aynı ret); `IN_PROGRESS` → "işleniyor" (yalnızca eşik üstü belgede). Ardından `acquireStockLocks(plan)` → kurallar → defter + bakiye + rezervasyon + belge durumu + `appendAudit` + gerekiyorsa `enqueue(tx, …)` → numara (§7) → idempotency `COMPLETED` + beyaz listeli sonuç → commit.
3. **Ret (M-1):** iş kuralı reddi (`INSUFFICIENT_STOCK`, `TRACKING_VIOLATION`, `LOCATION_LOCKED`, `REVERSAL_BLOCKED`, `DOCUMENT_STATE`, `VALIDATION_FAILED`) ana transaction'ı geri alır; ardından **ayrı kısa transaction**'da (`withMembership` + zaman aşımları) idempotency satırı `REJECTED` + `error_code` + `request_hash` + `actor_user_id` ile `INSERT … ON CONFLICT DO NOTHING` yazılır (yarışta önce yazılan kazanır; çakışmada mevcut kayıt §2 kurallarıyla değerlendirilip onun sonucu döner). Aynı anahtar + aynı içerik → aynı ret; aynı anahtar + farklı içerik → `IDEMPOTENCY_MISMATCH`. İstemci düzeltilmiş istek için **yeni anahtar** üretir. Kalıcı saklanmayan sonuçlar: `IDEMPOTENCY_MISMATCH` (kayıt zaten var), geçici hatalar (`VERSION_CONFLICT` tükenmesi, bağlantı, `FORBIDDEN`/`UNAUTHENTICATED` — yetki değişebilir) → aynı anahtarla yeniden denenebilir. Ret kaydı yazılamazsa (ikinci transaction hatası) istemciye asıl ret kodu döner ve hata loglanır; stok etkisi zaten yoktur.
4. **Yeniden deneme:** `40P01`, `40001`, `55P03` → tüm transaction en çok 3 kez, jitter'lı (A-75); iş kuralı hataları denenmez; tükenirse `VERSION_CONFLICT` + `retryable: true`.
5. **Zaman aşımı:** her stok transaction'ında transaction-local `set_config` (G-02 uyumlu), `withMembership`'in ilk ifadesinden hemen sonra (§2).
6. **Eşik üstü belge (AC-36, A-07; M-5, M-6, MINOR-7):**
   - İstek transaction'ı (≤ 200 satır sınırı aşıldığında): belge kilitli (`FOR UPDATE`, sürüm denetimi) → `APPROVED` kalır, `posting_job_id` + `posting_requested_by = çağıran` yazılır, idempotency `IN_PROGRESS` commit edilir ve `enqueue(tx, { type: "stock.document.post", actorUserId: <istek sahibi>, payload: { documentId, idempotencyRecordId }, singletonKey: documentId })`.
   - **İşleme kilidi:** `posting_job_id IS NOT NULL` iken `cancelDocument`, `updateDraft`, `reserve`/`release`, yeni anahtarla `postDocument` → `DOCUMENT_STATE` (belge satırı kilitli okunarak denetlenir).
   - **Worker:** `actorUserId` = istek sahibi; `withMembership(stock.post)` o kullanıcının **güncel** yetkisiyle (ADR-016 §6); kilitli belgede `status = 'APPROVED' ∧ posting_job_id = ctx.jobId` değilse iş etkisiz biter (ör. iptal yarışı kazanıldıysa; yalnızca log). Başarı: aynı 7 adım tek transaction'da, aynı idempotency satırı `COMPLETED`, `posting_job_id` temizlenir, `processed_events` aynı transaction'da (ADR-019 §2).
   - **Kalıcı hata (iş kuralı reddi, yetki kaybı):** ana transaction geri alınır; **ayrı transaction**'da idempotency `FAILED` + `error_code`, belgede `posting_job_id = NULL` (`APPROVED` kalır), durum geçmişi + audit ve `processed_events` satırı birlikte yazılır → yeniden teslim etkisiz biter; pg-boss işi kalıcı başarısız işaretlenir. Geçici hata → pg-boss yeniden dener (ayrı transaction yazılmaz).
   - > 2.000 satır → `VALIDATION_FAILED`/`DOCUMENT_TOO_LARGE`.
   - **Uzun kilit (MINOR-12):** worker 2.000 satıra kadar kilit tuttuğundan senkron komutlar aynı boyutlarda `55P03` → 3 deneme sonrası `VERSION_CONFLICT` görebilir; T-222 ve T-231 eşik üstü transaction süresi ile eşzamanlı senkron komutların `VERSION_CONFLICT` oranını ölçer; kabul edilemezse A-07/A-75 yeniden değerlendirilir.
7. **Kilit sırası eki (MINOR-2):** `acquireStockLocks` adımları (I-15) değişmez; komutlar ek kilitleri yalnızca şu sırayla alır: (a) idempotency satırı (anahtar tekil), (b) `acquireStockLocks` (belge → sayım kilidi → boyut/bakiye → rezervasyon → seri), (c) **en son** `number_sequences` satırı (ters kayıt numarası dahil). `ensureDimensions` sıralaması: boyut doğal anahtarı `(item_id, location_id, lot_id, serial_id, stock_status, inventory_owner_id, handling_unit_id)` sırasıyla, NULL'lar ilk (`NULLS FIRST`), UUID'ler ikili/`uuid` karşılaştırmasıyla; uygulama sıralaması SQL `ORDER BY … NULLS FIRST` ile birebir (T-210 birim testi). Ters kayıt planı `document` = asıl belge; yeni ters belge INSERT edilir.
8. **Hata kodları ve HTTP:** `INSUFFICIENT_STOCK` 409, `TRACKING_VIOLATION` 422, `LOCATION_LOCKED` 423, `REVERSAL_BLOCKED` 409, `IDEMPOTENCY_MISMATCH` 409, `COUNT_LOCK_ROW_MISSING` 500 (alarm); `15-engineering §Hata sözleşmesi`ne T-203 işler.

**Sonuçlar ve riskler:**
- Reddedilen isteğin anahtarı yeniden kullanılamaz — UI her yeni form açılışında anahtar üretir, "yeniden dene" yeni anahtar alır.
- Ret kaydı için ikinci transaction ek gecikme getirir (yalnız ret yolunda).
- Idempotency kayıtlarının saklama süresi A-73; `result` beyaz listeli (ADR-017 §10).

**Doğrulama:** AC-02, AC-03 (T-220: tekrar başarı ve tekrar ret aynı sonucu döner, farklı içerik/aktör → `IDEMPOTENCY_MISMATCH`); AC-27 (T-227); AC-36 ve işleme sırasında iptal (T-228, T-230); `retry` ve kilit sırası birim testleri (T-213, T-210).
